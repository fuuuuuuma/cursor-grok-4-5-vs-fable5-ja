# 🎁 Cursorで使えるSkills100選

Cursorの `.cursor/skills/<skill名>/SKILL.md` にそのまま置いて呼び出せるスキル集です。Agentが必要なときに自動で読み込んで実行します。

**受け取り方**: 使いたいSkillのコードをコピーし、`.cursor/skills/<skill名>/SKILL.md` として保存してください。フォルダ名とnameを揃えるのがコツです。

## 1. コードレビュー・品質

### 1. pr-self-review
用途: PR作成前に自分の差分を機械的にセルフレビューする ｜ 保存先: .cursor/skills/pr-self-review/SKILL.md
```text
---
name: pr-self-review
description: PRを開く前・git pushする前に、差分を自分でレビューして指摘を洗い出すときに使う。
---

# PR Self Review

## いつ使うか
- 「PRを出す前にレビューして」と言われたとき
- git push直前で差分の最終チェックをしたいとき

## 手順
1. `git diff main...HEAD` で変更範囲を取得する
2. 変更ファイルごとに、命名・エラーハンドリング・未使用変数・TODO残りを確認する
3. 指摘は「ファイル名:行番号 + 問題点 + 修正案」の形式でリスト化する
4. 致命的な問題があれば、レビュー結果を出す前に修正案を提示する

## 注意
- 指摘は具体的な行番号付きで出す。抽象的な感想で終わらせない
- 動作確認していない修正案は「未検証」と明記する
```

### 2. security-review
用途: 変更コードにセキュリティ上の懸念がないか確認する ｜ 保存先: .cursor/skills/security-review/SKILL.md
```text
---
name: security-review
description: 認証・入力処理・外部通信・シークレット扱いを含むコードを書いたとき、または明示的にセキュリティレビューを依頼されたときに使う。
---

# Security Review

## いつ使うか
- APIキー、パスワード、トークンを扱うコードを変更したとき
- ユーザー入力を直接SQL/シェル/HTMLに渡すコードがあるとき
- 「セキュリティチェックして」と言われたとき

## 手順
1. 変更ファイルから、入力値・認証情報・外部リクエストを扱う箇所を洗い出す
2. SQLインジェクション、XSS、コマンドインジェクション、ハードコードされた秘密情報の有無を確認する
3. `.env` や設定ファイルにシークレットが平文で入っていないか確認する
4. 見つかった問題を重大度（高/中/低）付きでリスト化する

## 注意
- 秘密情報を発見した場合、コミット履歴に残っていないか合わせて警告する
- 誤検知の可能性がある指摘は「要確認」と明記し断定しない
```

# Lint Fix

## いつ使うか
- `eslint` / `ruff` / `golangci-lint` 等がエラーを出しているとき
- コミット前にスタイル統一したいとき

## 手順
1. プロジェクトのlintコマンド（package.jsonやMakefile等）を確認して実行する
2. 自動修正オプション（--fix等）で直せるものは先に直す
3. 自動修正できない指摘は、意味を変えない範囲で手動修正する

## 注意

- 既存のlint設定ファイルを勝手に緩めない

# Complexity Audit

## いつ使うか

## 注意
- 数値化ツールがあれば併用するが、無ければ目視基準で代替してよい

## いつ使うか

# memory-footprint-reducer

## いつ使うか
- インフラコスト削減のためメモリ使用量を見直すとき
- 「メモリ使用量が大きい」と指摘されたとき

## 手順
1. 起動直後と負荷時のメモリ使用量を計測し、ベースラインを把握する
2. メモリスナップショットで大きな割合を占めるデータ構造・キャッシュを特定する
3. 不要に全件保持しているキャッシュ・配列がないか、必要な範囲に絞れないか検討する
4. 削減後に同じ計測を行い、機能に影響が出ていないことも合わせて確認する

## 注意
- メモリ削減とレスポンス速度はトレードオフになる場合があるため両方計測する
- キャッシュを削りすぎてDB負荷が増えていないか併せて確認する

### 99. dependency-update-batcher

# dependency-update-batcher

## いつ使うか
- 依存パッケージの更新が長期間放置されているとき
- 自動更新PRが大量に溜まっているとき

## 手順
1. 更新対象パッケージを一覧化し、パッチ/マイナー/メジャーに分類する
2. パッチ・マイナー更新は破壊的変更が少ないためまとめて1バッチにする
3. メジャー更新は1パッケージずつ個別に更新し、リリースノートで破壊的変更を確認する
4. 各バッチ更新後にテストを実行し、問題なければ次のバッチに進む

## 注意
- 一度に全パッケージを更新してテストが落ちた場合、原因の切り分けが困難になるため段階的に行う
- メジャー更新はコード修正が必要な場合、別タスクとして切り出す
