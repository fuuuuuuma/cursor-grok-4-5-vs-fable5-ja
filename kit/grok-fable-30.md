# 🎁 Grok 4.5 × Fable 5 使い分け30選

Cursorの2大モデルを、精度とコスパで賢く使い分けるための実践アイデアを30個まとめました。「速さと量のGrok 4.5」と「精度のFable 5」を、場面ごとに切り替えて使い倒しましょう。

**受け取り方**: 各アイデアの手順・プロンプトをコピーして、Cursorで試してください。

## 1. 下書きはGrok・仕上げはFable（速さと精度の二段構え）

### 1. 実装の一発叩き台をGrokで作る
狙い: 動くところまでを最速で形にする ｜ 使い分け: 骨組みはGrok 4.5 → 仕上げはFable 5
```text
Cursor Agentのモデルを手動でGrok 4.5に切り替え、まず「動くだけの一次実装」を作らせる。
プロンプト例: 「この関数の骨組みを最小構成で実装して。エラー処理や最適化は後回しでいい。まず動くものが欲しい」
Grok 4.5はSWE-Bench Proでタスクあたり約1.6万トークンと効率が高く、80トークン/秒前後の速度で叩き台の生成が速い。ここで完成度は求めず、次工程のFable 5に渡す土台作りに徹する。
```

### 2. Fableでレビュー・仕上げ磨き
狙い: 下書きの穴を精度の高いモデルで塗り直す ｜ 使い分け: Grokの出力→Fable 5に読み込ませて仕上げ
```text
Grok 4.5が作った下書きファイルをそのままFable 5に切り替えて渡す。
プロンプト例: 「このコードはGrok 4.5が書いた叩き台です。エッジケース・命名・エラーハンドリングを含めて仕上げレベルまで磨いてください」
CursorBench 3.2でFable 5 Maxは総合1位（70.5%）と精度面で優位なので、最終品質の担保はFable側に寄せる。
```

### 3. Grok下書き→Fableで設計欠陥だけ拾う二段レビュー
狙い: 全部読み直させず「設計判断」だけをFableに絞って見せる ｜ 使い分け: 実装完了後の設計レビューのみFable 5
```text
Grok 4.5で実装まで終えたら、Fable 5には差分全体ではなく「設計上の懸念点」だけを聞く。
プロンプト例: 「このPR差分について、実装の細部ではなく設計判断（責務分割・拡張性・将来の変更コスト）だけを指摘して」
論点を絞ることでFable側のトークン消費を抑えつつ、精度が要る部分だけに投資できる。
```

### 4. リファクタリングの一次案をGrok、影響範囲確認をFableで
狙い: リファクタの手数はGrokに任せ、壊れないかの判断だけFableに聞く ｜ 使い分け: 変更適用=Grok 4.5、影響範囲判定=Fable 5
```text
Grok 4.5に「この関数をこの方針でリファクタリングして」と一次案を作らせた後、Fable 5に切り替えて確認する。
プロンプト例: 「このリファクタリング差分が既存の呼び出し元・テストに与える影響を洗い出して。壊れる可能性がある箇所だけ教えて」
影響範囲の見立ては精度が命なので、ここだけFable 5に切り替える。
```

### 5. テストコード雛形はGrok、エッジケース洗い出しはFable
狙い: テストの「量」はGrokで、「質」の穴埋めはFableで担保する ｜ 使い分け: 雛形量産=Grok 4.5、抜け漏れ検出=Fable 5
```text
Grok 4.5に「この関数の正常系テストを一通り書いて」と依頼し、まず数を揃える。
その後Fable 5に切り替えて「このテスト一覧に抜けているエッジケース・異常系を指摘して」と聞く。
量産と精査を別モデルに分けることで、両者の強みを無駄なく使う。
```

## 2. 大量処理・反復作業はGrok 4.5で回す

### 6. 大量ファイルへの同一パターン適用
狙い: 単純作業をコスパよく高速処理する ｜ 使い分け: 反復的な一括変更はGrok 4.5に固定
```text
複数ファイルに同じ変更を機械的に適用するタスク（例: import文の統一、共通ヘッダーの追加）はGrok 4.5に任せる。
プロンプト例: 「対象ファイル一覧に対して、同じルールでこの変更を適用して」
判断の分岐が少ないタスクは、入力$2/出力$6（100万トークンあたり）というコスト構造が効いてくる。
```

### 7. ログ/データ変換バッチ処理
狙い: 定型的な変換作業を安く速く終わらせる ｜ 使い分け: フォーマット変換・パース系はGrok 4.5
```text
ログファイルやCSVの整形、JSON⇔YAML変換のようなスクリプト生成はGrok 4.5に依頼する。
プロンプト例: 「このログ形式をこのスキーマのJSONに変換するスクリプトを書いて」
ロジックの正確な設計判断が不要な変換タスクは、生成速度約80トークン/秒の恩恵を受けやすい。
```

### 8. 単純なリネーム・import整理の一括処理
狙い: 機械的な整理をコストをかけずに済ませる ｜ 使い分け: リネーム・整理系はGrok 4.5、命名方針の相談だけFable
```text
変数名やファイル名の一括リネーム、未使用import削除のような機械的作業はGrok 4.5に流す。
命名の方針自体に迷う場合だけ「この命名規則、チーム的に適切か」とFable 5に一言確認する程度に留める。
```

### 9. ドキュメント/コメントの大量生成
狙い: 網羅性が要るドキュメント作業を効率よくこなす ｜ 使い分け: 一次ドラフト生成はGrok 4.5、公開前の校閲はFable 5
```text
関数コメントやREADMEの叩き台をGrok 4.5でまとめて生成する。
プロンプト例: 「このモジュール内の全関数にdocstringを追加して」
公開ドキュメントとして出す前の最終チェックだけFable 5に切り替えて誤りがないか確認する。
```

### 10. Cloud Agentでの並列タスク分散にGrok
狙い: 複数タスクを同時進行させてもコストを抑える ｜ 使い分け: 並列実行するCloud Agentの実装枠はGrok 4.5
```text
Cursor Cloud Agentで複数タスクを並列に走らせる際、実装量が多いタスクはGrok 4.5を割り当てる。
タスクあたりのトークン消費が上位モデル比で約4.2倍効率的（約1.6万トークン vs 約6.7万トークン）なので、並列数を増やしてもコストが跳ねにくい。
設計判断が絡む1本だけFable 5に割り当てるなど、タスクの性質でモデルを混在させる。
```

## 3. 難所・設計判断はFable 5に任せる

### 11. アーキテクチャ設計・技術選定
狙い: やり直しが効かない意思決定を精度優先で行う ｜ 使い分け: 設計・選定フェーズはFable 5固定
```text
新機能のアーキテクチャ設計や、ライブラリ選定のような後戻りコストが大きい判断はFable 5に任せる。
プロンプト例: 「この機能を実装するにあたり、想定される3つの設計アプローチとそれぞれのトレードオフを整理して」
CursorBench 3.2で総合1位のFable 5 Maxを、間違えると手戻りが大きい局面に投入する。
```

### 12. 難解なバグの根本原因調査
狙い: 表面的な修正でなく根本原因を突き止める ｜ 使い分け: 再現困難・原因不明のバグはFable 5
```text
何度直してもぶり返すバグや、再現条件が不明なバグの調査はFable 5にPlan modeで依頼する。
プロンプト例: 「このスタックトレースとログから、考えられる根本原因を複数仮説立てて、それぞれの検証方法も示して」
精度が要る推論タスクほどFable側の強みが活きる。
```

### 13. セキュリティに関わる実装
狙い: 見落としが致命傷になる領域を慎重に扱う ｜ 使い分け: 認証・権限・入力検証はFable 5
```text
認証まわり、権限制御、外部入力のバリデーションのような、見落としが事故に直結する実装はFable 5に任せる。
プロンプト例: 「この認証フローの実装に、想定される脆弱性（インジェクション・権限昇格など）がないかレビューして」
コストよりも精度を優先すべき領域なので、迷わずFable 5を指定する。
```

### 14. 複雑な並行処理・非同期設計

```text
複数スレッド/非同期処理が絡む設計は、Fable 5にPlan modeで事前検討させてから実装に入る。
プロンプト例: 「このワーカー間のデータ共有パターンで、競合状態やデッドロックが起きうる箇所を洗い出して」
バグが本番でしか顕在化しにくい領域ほど、事前の精度の高い設計レビューが効く。
```

### 15. パフォーマンスクリティカルなアルゴリズム設計
狙い: 計算量やメモリ効率が結果を左右する箇所を丁寧に詰める ｜ 使い分け: アルゴリズム選定・計算量の検討はFable 5

```text
大量データ処理やリアルタイム性が求められる箇所のアルゴリズム設計はFable 5に相談する。

実装自体はGrok 4.5に渡してよいが、方針決定はFable 5で固めてから着手する。
```

## 4. コストを管理しながら使い分ける

### 16. タスクの難易度で事前に振り分けるルール表を作る
狙い: 毎回悩まず機械的にモデルを選べるようにする ｜ 使い分け: チーム内でGrok/Fableの適用基準を明文化
```text
「単純作業・反復作業はGrok 4.5」「設計判断・重要な修正はFable 5」という振り分けルールをNotionやREADMEに書いておく。
迷う時間そのものがコストなので、Cursorを開く前に判断できる状態を作っておくのが実質的な節約になる。
```

### 17. トークン消費をダッシュボードで定期チェック
狙い: 使いすぎに気づかないまま月末を迎えない ｜ 使い分け: 消費傾向を見てGrok比率を調整する
```text
Cursorの使用量ダッシュボードを週次で確認し、Fable 5への偏りが大きければ次週は反復系タスクを意識的にGrok 4.5に振る。
数字で見て初めて「この作業、実はGrokで十分だった」に気づけることが多い。
```

### 18. 反復系タスクの予算をGrokに固定配分
狙い: コストの見通しを立てやすくする ｜ 使い分け: 定型作業の予算枠をあらかじめGrok 4.5で確保
```text
月初に「定型的なコード生成・変換作業はGrok 4.5で」という運用ルールを決め、その分の予算を確保しておく。
入力$2/出力$6（100万トークンあたり）という価格を基準に、月間のタスク量から概算コストを見積もっておくと予算管理がしやすい。
```

### 19. Fableは「意思決定が必要な瞬間」だけに絞る
狙い: 高精度モデルを使うべき場面を絞り込みコストを抑える ｜ 使い分け: 実装作業ではなく判断が要る瞬間だけFable 5
```text
Fable 5を呼ぶのは「これで進めていいか迷っている時」だけ、というルールを自分の中に持つ。
プロンプト例: 「A案とB案、どちらで進めるべきか判断して」のような意思決定タスクに絞ることで、精度の高いモデルを本当に必要な場面だけに投入できる。
```

### 20. コスト超過アラートを設定し閾値でGrokに自動シフト
狙い: 予算超過に気づいた時点で運用を切り替える仕組みを持つ ｜ 使い分け: 閾値到達後は反復タスクを強制的にGrok 4.5へ
```text
月間予算の一定割合（例: 80%）を消費した時点で、以降の非重要タスクはGrok 4.5に固定するという自分ルールを決めておく。
Cursorの使用量表示を見て手動判断でもいいが、チーム利用なら閾値をSlack通知するなど仕組み化しておくと運用が安定する。
```

## 5. Autoと手動選択の使い分け

### 21. 迷ったらまずAutoに任せてみる
狙い: モデル選定に時間をかけずタスクに集中する ｜ 使い分け: 判断材料がない最初の一手はAuto
```text
どちらのモデルを使うべきか判断がつかない新規タスクは、まずCursorのAuto選択に任せてみる。
Autoが選んだモデルと結果を見てから、次回以降そのタスク種別を手動指定に切り替えるかを決める。
```

### 22. Autoの選定結果を見て次から手動指定に切り替える
狙い: Autoの傾向を学習材料にして自分の判断基準を育てる ｜ 使い分け: Auto実行後の振り返りで手動ルールを更新
```text
Autoが選んだモデルとその結果（速度・精度・コスト）を数回分メモしておく。
「このタスク種別はAutoだと大体Grokが選ばれる」と分かれば、以降はその種のタスクを最初から手動でGrok 4.5に指定して、Auto判定の時間すら省く。
```

### 23. Plan modeはFable固定、実行フェーズはAuto
狙い: 計画段階の精度は担保しつつ実行の柔軟性を残す ｜ 使い分け: Plan mode=Fable 5固定、Agent実行=Auto
```text
Cursor Plan modeでタスクの計画を立てる段階はFable 5を手動指定し、方針の精度を担保する。
計画が固まった後の実行フェーズ（Agentでの実装）はAutoに戻し、タスクの中身に応じてモデルを自動選択させる。
```

### 24. MCP/Skills連携タスクはAutoに任せる
狙い: 外部ツール呼び出しが絡む複雑なタスクをモデル任せで最適化する ｜ 使い分け: MCP/Skills経由の多段タスクはAuto
```text
複数のMCPツールやSkillsを跨いで実行するような、タスクの性質が読みにくい複合作業はAutoに任せる。
どのステップでどちらのモデルが適するかを人間が逐一判断するより、Auto側の最適化に委ねた方が結果的に速いことが多い。
```

### 25. Bugbot併用時はAutoでコスト最適化
狙い: レビュー自動化と生成モデルのコストを両立させる ｜ 使い分け: Bugbotの指摘対応はAutoに任せて総コストを抑える
```text
CursorのBugbotが指摘した軽微な修正はAutoに任せ、モデル側で難易度に応じた自動選択をさせる。
指摘内容が設計に関わる重大なものだった場合のみ、手動でFable 5に切り替えて対応する。
```

## 6. 検証で過信を防ぐ（報酬ハッキング対策）

### 26. 出力を鵜呑みにせずテスト実行で検証する
狙い: モデルの回答をそのまま信じるリスクを減らす ｜ 使い分け: どちらのモデルの出力でも実行結果で必ず裏取り
```text
Grok 4.5・Fable 5どちらの出力であっても、「テストが通った」という報告だけで完了扱いにしない。
実際にCursor上でテストコマンドを実行し、出力ログを自分の目で確認してから完了と判断する。
高性能モデルほどベンチマークで既存の修正を参照する「報酬ハッキング」傾向が指摘されており、実運用でも同様の注意が要る。
```

### 27. Web検索由来の修正でないか出典を確認する
狙い: 借用元の存在を把握したうえで採用可否を判断する ｜ 使い分け: モデルが根拠を示した場合は出典URLを実際に開く
```text
モデルが「この実装は一般的な手法です」と説明した際、根拠となる情報源を尋ねて実際に確認する。
プロンプト例: 「この修正案の参考にした情報源やパターンがあれば教えて」
Web上の既存コードをそのまま流用している場合、ライセンスや文脈の違いによる不整合がないかを人力で見る。
```

### 28. Git履歴からの「借用」を疑い差分を人力チェック
狙い: 既存コードのコピペで一見動くだけの修正を見抜く ｜ 使い分け: 差分の妥当性は最終的に人間がgit diffで確認
```text
モデルが提示した修正差分を、必ず`git diff`で自分の目で読んでからコミットする。
特に「過去のコミットやリポジトリ内の別実装と酷似した変更」は、文脈が合っているかを重点的に確認する。
自動生成の速さに引っ張られてレビューを省略しないことが、報酬ハッキング対策の基本になる。
```

### 29. 二重チェック体制: Grok実装→Fableレビュー→人間承認
狙い: モデル2段+人間の三重チェックで精度とコストを両立する ｜ 使い分け: 実装=Grok 4.5、レビュー=Fable 5、最終承認=人間
```text
重要度が中程度以上のタスクは、Grok 4.5で実装→Fable 5でレビュー→人間が最終承認、の三段構えにする。
プロンプト例（レビュー段階）: 「この実装に技術的な誤りや見落としがないか、批判的な視点でチェックして」
どちらのモデルの評価も鵜呑みにせず、最終判断は必ず人間が行う運用を崩さない。
```

### 30. ベンチマークスコアを過信しない運用ルールを明文化
狙い: 数字だけでモデル選定を決めきらない姿勢を保つ ｜ 使い分け: CursorBenchのスコアは参考値、最終判断は実タスクの結果で
```text
CursorBench 3.2でFable 5 Maxが総合1位（70.5%）、Grok 4.5 Highが3位（66.7%）という数値はあくまで参考値として扱う。
自分たちのプロジェクトの実タスクでは、精度差がスコアほど体感されない場面や、逆にGrokのコスパが刺さる場面もある。
「ベンチマークは選定の入り口、最終判断は自分たちの実測」という運用ルールをチームで共有しておく。
```
